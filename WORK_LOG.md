# Work log

- 2026-10-06: Added local SparkBot USB chassis diagnostics and a host CLI. Movement pulses stop on the head after 300 ms, including missing echoes and initial write failure; concurrent remote chassis commands return busy. The ESP32-S3 build passes with 48% of the app slot free. Host tests: 161 run, 2 skipped, all remaining tests pass, including 5 new diagnostic cases. Backed up the attached head's full flash and updated only its active app slot; esptool verified the write. Physical boot reached the application once without panic; pairing and saved Wi-Fi remain intact. USB stop-probe and a 300 ms forward/stop pulse each reported successful local writes but zero UART response bytes. The owner confirmed no chassis movement during the USB pulse, but observed a brief chassis movement at its own power-on. Further diagnosis requires checking contact continuity and the installed base firmware. The original head flash contains the same forward and reverse command strings; the matching upstream v1.9.4 board configuration uses the same UART pins and baud rate.
- 2026-10-07: The ESP-SparkBot now offers everything its head can reach. Chassis: `chassis.drive` (forward/turn -1..1, duration up to 10 s, repeated every 200 ms by a task since the base stops itself after 500 ms), `chassis.move` with a duration, `chassis.stop`, `chassis.dance`, `chassis.set_light` by name, `chassis.status`; results say whether the base echoed. `imu.read` through a vendored copy of Espressif's BMI270 driver (components/bmi270), extended to the BMI260 that this unit turned out to carry (chip ID 0x27; Bosch's BSD-3-Clause configuration file via ChromiumOS EC). `camera.capture` on the OV2640 through a new esp32-camera backend (components/camera/camera_dvp.c); the command is now generic (`CONFIG_IMPO_CAMERA`, impo_camera.c) rather than the Watcher's. The top touch pad is the talk button and the side pads the aux button (sparkbot_touch.c, IDF's touch_sens driver with the factory demo's thresholds); the battery is read on ADC2 channel 3. Host test tests/test_sparkbot_console.py rewritten for the base task (10 cases). On hardware: touch pads trigger, the BMI260 reads upright at z = +1 g, battery 87%. Not yet verified: the other orientation names, the camera, and the base (the owner hadn't seated the head on it). The pin, baud and command strings match xiaozhi-esp32's esp-sparkbot board exactly. Later that day, with the owner at the device: the unit carries a GC2145, not an OV2640, so the DVP backend takes RGB565 and encodes it with esp_new_jpeg (~250 ms for VGA; esp32-camera's own encoder took ~2 s). Three things broke consecutive photos before that was settled: the USB diagnostic ran on the 3.5 KB serial task (now its own 8 KB task), esp32-camera's PSRAM-DMA mode loses sync whenever the CPU works in PSRAM (off now; the DMA pieces are capped at 16 KB so internal RAM can hold them), and the sensor is left running after the first photo since deinit + init on the S3 returned scrambled frames. Photos over USB verified the scene (a wall, a door and a chair; the owner wasn't in view). All 166 host tests pass with managed_components fetched. Still unverified on hardware: the base (not seated), the touch pads as buttons (one side pad registered once), and the orientation names other than upright.
- 2026-10-08: With the base charged it answered and drove: lights, forward, back and left over the USB diagnostics (now also `>chassis=light=<effect>` and `>chassis=forward:1000`, up to two seconds). An unpowered base still echoes bytes (its C2 runs off the head's TX line through the RX pin's protection diode) while moving nothing, so "responding" proves the link, not power. The head was given the local Wi-Fi over USB (`>wifi.ssid=`, `>wifi.pass=`, `>wifi.connect` restarts it) and came online at gadgets.impo.ai with all 17 commands registered; `imu.read`, `device.health`, `display.show_text`, `chassis.*` ran through the gateway's admin invoke. Command results had lost their data on the way: Link forwards only ok, error and payload, so impo_commands_run now gathers everything else under payload. Open: a gadget whose saved Wi-Fi is gone can only be re-pointed over USB; plan is to auto-start BLE phone setup after 60 s without the network, and an app entry to change a paired gadget's Wi-Fi.
