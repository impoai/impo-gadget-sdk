Impo Gadgets 架构与分层

一台硬件要变成 Impo 的 gadget，要穿过六层。下面标出每一层归谁：平台固定的、做硬件的人要动的、以及 agent 行为能被谁改。依据是 Impo fork 的 SDK 代码和 Muse 上游的结构，不是设想。

平台（Impo 维护，开源，接硬件的人不碰） Maker 定制（接一块新板子要写的） Agent 行为可定制的点 计划中

三种交互形状

命令（agent → gadget）link.invoke → link.result。一问一答，30 秒内。camera.capture、speaker.say、chassis.move 都是这一种。
事件（gadget → agent）link.event。离散、设备端去抖、网关 3 秒去重。被摇、被拿起、被放下；agent 的回答用 speaker.say 说出来。Muse 上游没有这一种。
观察流（计划）camera.watch {fps, seconds}：设备持续推帧，感知 worker 只把语义变化变成事件；主 agent 不在每帧循环里。

谁负责什么

要做的事动哪里不用动哪里
Maker接一块新板子一个板子文件填 impo_board_t；一个 sdkconfig 覆盖；在 features 里报它多出来的东西（陀螺仪、底盘）；登记到 board.sh / README。SparkBot 用了一个文件加两个小助手。协议、网关、服务端、App、UI、语音管线。板子一注册，agent 就看见它的能力。
Maker给板子加一条自己的命令板子文件里的 commands 表：名字、给 agent 读的描述、参数、一个不阻塞的 run。名字按 CAPABILITIES.md 的命名空间走；第二块板也要时，升格为公共命令并补契约。
Agent改 agent 对 gadget 的行为三个杠杆：服务端 prompt 里的 gadget 指令段（平台级）；每条命令自带的描述文字（Maker 级，这是 Maker 影响 agent 的方式）；skills/ 里的 SKILL.md（第三方设备级）。agent 本身的工具框架、投递机制、沙箱。
Agent接一台第三方设备（Sonos、Hue…）写一份 SKILL.md 教 agent 用它的局域网协议；gadget 只当桥（隧道）。固件对它一无所知；这是 Muse 的做法，隧道做好后 44 份上游 skill 直接复用。
平台加一种新能力（比如观察流）CAPABILITIES.md 先写契约 → 固件公共层 → 网关 → 服务端工具/worker → App。任何板子文件。
平台换 STT/TTS/视觉提供商只改服务端 voice/，key 在服务端密钥库。固件和网关：它们只认 /tts 和 /voice/* 接口。

和 Muse 上游的差别

Muse 有、我们保留

  • 板子接口 + 一板一文件，AGENTS.md 让 coding agent 做移植
  • link.register 自报命令表（commands_v2）
  • skills/ 用 prompt 适配第三方设备，固件只当桥
  • Noise 加密会话、BLE 配对、OTA、隧道

Muse 留空、我们填上

  • 回复朗读：上游 start_tts 是空位，我们接到 Gemini TTS（经网关 /tts）
  • speaker.say、speaker.play_url、camera.capture 通用化、imu.read、chassis.*
  • 能力词汇表（契约）和 capabilities 摘要
  • 内存预算：流式、用完即还

Muse 没有、我们新增

  • link.event：gadget 主动开口
  • 照片作为回合产物投递到 App
  • 服务端基础能力（STT / TTS / 看图）全在 Impo，gadget 零第三方 key
  • 计划：观察流 + 感知 worker
